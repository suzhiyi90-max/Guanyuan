# FE-170 / 现有 App 实际可玩性审查（代码证据版）

审查基线：`art/fe-170-exam-opening-assets` 当前分支；本报告基于 GitHub 读取到的源码，不代表本轮已启动浏览器运行预览。没有部署地址或可访问运行环境时，不把代码审查写成实际游玩测试。

## 1. 总体裁决

当前 App 是一个交互密度较高的“永济县令十日东堤案例”原型，具备可操作的调查、人物接谈、文书对勘、河工筹划、上宪互动、事件选择和若干档案界面。它不是完整的古代官员人生模拟器，也没有证据证明科举入仕、跨年人生、官职晋升和动态社会网络已形成完整可玩闭环。

原型已有场景切换、在场人物、接谈纸、案卷/账簿/证据链、焦点回查、动效与 reduced-motion 等设计，不应推翻重做；应保留其交互结构，将固定案例规则逐步替换为正式人生系统的通用规则。

## 2. 游戏循环逐项核验

| 环节 | 当前证据 | 判定 | 限制 |
|---|---|---|---|
| 新人生/进入游戏 | `App.tsx` 以 `GoalPrologue` 作为入口；`GameState.goalId` 初始为 null；选择志向后进入县令案头 | 实际可操作（固定案例开局） | 不是科举报名、考试、放榜、授官的人生起点；开局已默认接印并收到东堤呈文 |
| 志向选择 | `GoalPrologue` 的 `onSelect={game.setGoal}` | 实际可操作 | 四种志向服务于同一个固定东堤案例，不是开放式人生目标体系 |
| 场景与移动 | `SceneArt` + 场景切换；界面明确标注移动不耗时段 | 实际可操作 | 当前核心场景主要是县衙、河堤、书斋，不能等同于完整开放地图 |
| 人物接触 | `ScenePresence` 根据时段与场景列出在场人物；接谈纸含寒暄、问话等入口；正式问人进入 `askPerson` | 实际可操作（预设人物） | 人物来自固定数据表，未证明科举、迁徙、任职等过程能动态生成全社会人物 |
| 人物关系 | 闻名/相识/共事/深交等认知深度与接触记录 | 部分可操作 | 当前关系与人物集合主要围绕案例预设，不能视为完整亲属、师生、同年、派系与跨地域关系网络 |
| 文书与证据 | 案卷、对勘、线索、账目并置、证据回查入口 | 实际可操作（案例内） | 内容和规则聚焦东堤、三百两账目等固定材料 |
| 行动与时段 | `periods = ['晨','午','暮','夜']`；`spendAction` 推进时段；夜间宴席有分支处理 | 实际可操作（有限规则） | 一般行动成本与特殊行动规则分散于具体回调；不是通用行动成本/休息/睡眠/起床系统 |
| 跨日与结局 | 初始第 1 日；`advancePeriod` 每四个时段递增一天；日程与结算针对第十日案例 | 实际可操作（十日剧本） | 第十日封顶逻辑和案例结局，不是人物完整生命周期或可持续年历 |
| AI 叙事 | `useNarrator` 支持供应商配置、密钥、流式输出、缓存、解析校验、失败回退；候选选项经 `resolveGeneratedEvent` 处理 | 有条件可操作 | 需用户配置兼容接口与密钥；不是默认开箱可用；生成内容须经过解析与效果白名单 |
| AI 与正式事实 | AI 生成事件保存在独立 narrative store；运行时以 handledEvents 等记录已决状态，效果由受限映射应用 | 部分接通 | 当前证据不能证明它已统一进入 W5 事件账本/完整存档链；必须单独核对两条状态链的一致性 |
| 自动保存 | `useGuanyuanGame` 使用 `localStorage` 的 `guanyuan.save.v1` 写入游戏状态；叙事配置另用独立 key | 实际可操作（本机原型存档） | 这是该分支当前 App 的 localStorage 方案，不能直接等同于 W5 IndexedDB Full/Incremental 存档链 |
| 恢复 | `loadSave` 读取并做少量字段形状检查后与 initialState 合并 | 部分可操作 | 轻量容错，不是完整事件账本校验、从 genesis 重放的强一致恢复 |
| 导出 | `App.tsx` 导出 `guanyuan.save.v1` JSON | 实际可操作（底稿导出） | 当前代码片段中没有与 W5 便携包契约等价的完整校验/签名/链验证导出 |
| 导入/多档/安全删除 | 本次检查的 App/useGame 代码未看到对应完整流程 | 未能在该 App 代码路径确认 | W5 分支另有实现，不能把它自动算作当前运行 App 已接通 |
| 桌面/平板/手机真实视觉 | CSS 与组件具备响应式、焦点、动效和 reduced-motion 代码 | 未能实测 | 本轮没有实际可访问的运行预览和三档视口截图，不作运行画面通过结论 |

## 3. 关键代码证据

- `app/src/App.tsx`：入口通过 `GoalPrologue` 选择志向；主场景使用 `SceneArt`、`ScenePresence`；含今日案头、案卷、事务、人情、账房、生活等栏目。
- `app/src/game/useGame.ts`：初始状态为第 1 日、晨时、已有县令身份叙事（接印并收到东堤呈文）、初始证据 `E-001` 与 `P-006`；四时段推进；第十日案例结算。
- `app/src/components/ScenePlate.tsx`：场景专图通过资源注册表读取；支持加载/失败状态、fallback 和 pending 提示；在场人物可进入接谈纸。
- `app/src/narrative/useNarrator.ts`：AI 叙事候墨、流式生成、缓存、解析、超时和失败回退。
- `app/src/narrative/store.ts`：AI 配置/事件与密钥分别存放于两个 localStorage key；密钥不进入配置导出。
- `app/src/sceneArt.ts`：FE-170 已预留科举院落、考场、拜谒厅堂及放榜框、桌案、惊堂木资源路径，当前均为 `src: null` / `pending: true`。

## 4. 当前最重要的结构性缺口

### P0（下一阶段设计/集成前置）

1. **明确运行时唯一权威状态链。** 当前 App 的 `guanyuan.save.v1` localStorage 状态与 W5 IndexedDB/EventLedger 存档实现不能被默认视为同一个运行时。必须先画清当前 App 实际挂载的状态仓储、命令入口、事件账本、投影、保存与恢复路径，避免“双存档、双事实源”。
2. **明确 AI 事件的事实提交边界。** AI 叙事当前有独立存储与受限效果应用；必须证明候选确认后如何进入正式事件账本、如何回放、如何随档导出恢复。没有证据前不得把“AI 可生成候选”称为“AI 已进入正式世界事实链”。

### P1（正式人生功能施工前）

1. 将固定“十日东堤案例开局”改为可配置的人生起点：科举报名、考试、成绩/名次、放榜、授官与首日入职；当前用户提供的院落、考场、榜框资源为该阶段视觉素材。
2. 将四时段与固定十日限制抽象为可持续时间系统，支持睡眠、起床、休息、行动耗时、跨日/跨年和人物生命周期。
3. 将预设人物表与案例关系扩展为由科举、籍贯、任职、亲属、师生、同年、组织与地理流动生成的社会网络。
4. 将“在场接谈”与远程通信分开：同场直接交谈；异地通过书信/差遣等渠道，结算送达、耗时、费用、误解、回信与等待期间世界推进。
5. 人物详情与关系图需从玩家可认知信息出发，支持信息来源、误判、秘密、履历、利益、资源与行动历史，而不只是静态人物卡。

### P2（后续质量补齐）

1. 当前 App 的导出、恢复和 W5 存档链建立同一套契约测试。
2. 对桌面/平板/手机运行截图、资源加载、键盘/触屏和 reduced-motion 做真实浏览器验收。
3. 继续完成 FE-170 美术二进制入库；资源文件实际存在、路径可加载后才能取消 pending。

## 6. 下一阶段施工顺序（建议基线）

1. **W5/App 运行时接线审计**：确认当前运行 App 是否已切到 IndexedDB/EventLedger；若未切，先完成唯一权威状态链设计与迁移，不增加新玩法。
2. **AI 事实链一致性审计**：确认生成候选、玩家选择、效果验证、事件追加、状态重放、保存恢复的闭环。
3. **新人生/科举起步垂直切片**：使用 FE-170 场景资源；先完成报名→考试→放榜→授官→首日，不扩展十种考试玩法。
4. **通用时间与行动成本**：在垂直切片上接入可持续时钟、休息、睡眠、行动成本和跨日推进。
5. **人物与社会关系底座**：人物身份生成、关系形成、认知边界、同场/远程交往。
6. **既有东堤案例迁移**：保留为可复用的中期县令事件章节，不再作为所有新人生的唯一固定开局。

## 7. 验收边界

本报告为源码审计，不是运行时验收。后续需提供可访问预览或可运行环境，完成 1440px / 1024px / 390px 实际操作、刷新恢复、AI 候选确认、存档往返和截图证据。美术资源需单独通过内容、文件、接线、运行四关。

## 8. 重要分支边界补充：W5 运行时尚未进入 FE-170 当前基线

进一步核对 PR 基线后，发现必须明确区分两条并行施工线：

- PR #69（FE-170）base 是 `docs/fe-169-art-asset-workflow`，其基线来自 `main`（`80398f5f...`）。
- PR #60（W5-D3B）base 是 `work/w5-d3-runtime-startup-restore`，head 是 `work/w5-d3b-app-startup-lifecycle`。
- PR #60 的 diff 已把 `App` 包装为启动恢复门，并在 `useGuanyuanGame` 中接入 IndexedDB 仓储、单档自动恢复、多档显式选择、事件重放和串行保存。
- 但 PR #60 仍为 Draft/Open，且其分支不在 PR #69 的祖先链中。

因此，本报告第 2 节对 `localStorage` 的判断准确描述的是 FE-170/PR #69 当前所基于的 App 代码，不应被误读为 W5 分支也仍然只用旧存档。反过来，也不能把 PR #60 的代码能力算作当前 FE-170 分支已经拥有的能力。

**集成阻断：** 现阶段 FE-170 的科举美术接入分支与 W5 运行时施工线尚未合流。下一步必须在不丢失任一侧成果的前提下，建立明确集成基线：先完成 W5 主线全链路审计与运行时启动恢复验收，再把 FE-169/170 美术图位与视觉规范移植/合并到 W5 已接通运行时的 App 基线上。不能直接从 main 继续叠加玩法，也不能让 FE-170 旧版 `useGame` 覆盖 W5 的新运行时实现。
