## 二、命令边界与失败成本

### 已有实现基础

当前 W5 预览运行时：

- `runtime-orchestrator.ts` 是玩家事实写入入口：先做事件 schema 校验，再追加候选账本事件，随后从账本重建投影；只有投影成功才返回新 session。
- 事件追加拒绝、幂等重复、幂等冲突、schema 失败或 replay 失败时，session 的账本和业务投影保持原值；无效候选不会成为已提交事实。
- `event-ledger.ts` 以 worldId + source + intentKind + actor + clientRequestId 组成幂等键；请求时间、事件种类和 payload 进入 fingerprint。相同请求返回原事件，内容变化则冲突。
- `event-replay.ts` 先验证完整事件区间和 schema，再执行纯 reducer；reducer 失败不返回部分投影。
- 预览 reducer 在业务前置不满足时抛出 replay rejection；orchestrator 不替换 session，因此无效业务候选不会进入正式账本状态。

### 仍缺的产品契约

1. **发起前拒绝 vs 已受理后失败：** 总纲区分“无法发起”和任务执行后的失败/偏差，但没有统一列出哪些校验失败不扣成本、哪些命令一经受理即支付发起成本、哪些执行失败仍消耗时间/资源。
2. **部分成功与部分失败：** 10.7 及行政执行章节允许部分完成、延迟、资源不足、权限/程序阻塞、能力不足、利益冲突、外部变化等结果；缺少这些结果对发起成本、已消耗资源、已完成子任务、剩余任务和责任记录的统一规则。
3. **玩家撤回/改令/重试：** 未明确已受理任务能否撤回、撤回费用、重新委托是否新任务、重复点击/网络重试与玩家主动重新发起如何区分。
4. **执行人拒绝/失联/被替换：** 需要明确任务仍有效、暂停、转交、失败或重开时的状态转换；不得把“执行人拒绝”误记成玩家命令未发起。
5. **成本归属：** 时间、银钱、差遣资源、礼仪成本、机会成本需要区分发起时扣除、执行中逐步扣除、检查点扣除、失败后沉没成本和可退回资源。
6. **同一命令多副作用：** 一次命令若同时扣预算、建立任务、发文书、改变关系、占用时段，必须一个事务提交或通过有明确补偿规则的事件链；不能半成功而 UI 显示全成功。

### 建议统一命令结果语义

以下是建议的结果类别，不是现有 schema：

| 结果类别 | 是否成为权威事件 | 发起成本建议 | 时间推进 |
|---|---|---|---|
| invalid / unauthorized / precondition-rejected | 否 | 不扣 | 不推进 |
| accepted | 是，记录受理及发起成本 | 按命令定义扣发起成本 | 按声明占段 |
| executing / checkpointed | 是，记录阶段结果 | 按阶段/资源规则结算 | 按世界时钟推进 |
| completed / partially-completed | 是，记录实际成果 | 已发生成本不回滚 | 继续按时钟推进 |
| delayed / blocked | 是，记录原因与下一检查点 | 已发生成本保留；未发生成本不预扣 | 世界照常推进 |
| failed / refused / cancelled | 是，记录责任与结果 | 按已发生事实结算，不统一全退/全扣 | 已经过时间不回滚 |
| duplicate request | 不新增事件，返回原结果 | 不重复扣 | 不重复推进 |

特别强调：玩家命令在受理前被拒绝，与已受理任务后来被 NPC 拒绝/执行失败，是两个不同事实。

## 三、任务与期限对象边界

当前总纲明确了任务异步、任务检查点与期限/债务结算，但对象分类和状态机仍需契约化。

建议至少分开以下对象（名称仅作逻辑分类，不是批准字段）：

| 逻辑对象 | 责任范围 | 建议最小契约 |
|---|---|---|
| CommandRequest | 玩家/NPC 发起的一次命令 | requestId、actor、intent、requestWorldTime、权限/前置结果、原结果引用 |
| Task | 已受理的执行工作 | taskId、目标、执行主体、责任主体、资源、状态、检查点、验收条件、结果事件 |
| TaskCheckpoint | 任务过程节点 | taskId、检查点序号、计划/实际时间、所需证据、完成/偏差结果 |
| TaskDeadline | 任务完成/检查点期限 | taskId、dueAt、priority、边界规则、是否已结算 |
| WorldDeadline | 汛期、工程、季节、制度日历边界 | 对象/规则引用、适用范围、有效时间、触发优先级 |
| ObligationDue | 人物承诺、债务、应付款等义务 | obligationId、责任主体、受益方、到期点、履行证据、一次性结算状态 |
| ResourceReservation | 尚未实际消耗但已被任务占用的资源 | 资源类型、预留量、释放/扣除条件、来源任务 |

**禁止把这些逻辑对象合并为一个“任务/期限”万能结构。** 任务截止、世界制度期限、私人承诺/债务分别由不同规则阶段处理；与 P1-A 建议一致，阶段 3/4/7 应各自处理唯一对象域。

## 四、时间戳与时间语义

### 当前实现已具备

- `WorldTime` 以 day + period（晨/午/暮/夜）表示离散世界时间。
- 账本事件包含 `requestWorldTime` 和 `committedAt`；校验要求二者合法且提交时间不早于请求时间。
- 事件 ID 按 worldId + seq 生成，序号确定事件账本顺序；回放按序号连续验证并重建。
- 当前 M1 运行时在同一离散时段接收并提交玩家意图，故 requestWorldTime 与 committedAt 通常相同。

### 缺口与建议

1. **发生时间与记录时间没有独立语义。** `requestWorldTime` 是命令请求时刻，不必然等于业务事实实际发生时刻；`committedAt` 是账本提交时刻，不等于历史事件发生时刻。未来补录、迟报、通信延迟、回忆和文书入档都需要区分 `occurredAt` 与 `recordedAt`（建议名称）。
2. **计划时间与实际时间缺失。** 任务需要 `scheduledAt`、`dueAt`、`startedAt`、`completedAt` 或检查点实际时间；不能把计划期限写成实际发生时间。
3. **精度与时区/日历边界。** 当前 WorldTime 是游戏内相对时间，不是现实时间戳；需要定义跨日、月份、季节、年号和历史日历换算，不应把现实 UTC 字符串直接混入 M1 四时段。
4. **迟报不等于迟发。** 事件可在发生后较晚才被玩家/系统记录；记录时间不得覆盖发生时间，排序/可见性须按事件类型决定。
5. **时间单调性范围。** 账本 seq 是写入顺序；事件 occurredAt 可能早于较早写入事件的发生时间（迟报）。因此不能简单要求所有 occurredAt 随 seq 严格递增；需要区分因果先后、记录顺序和世界时间有效性。
6. **同一边界排序。** dueAt 相同的任务/义务/环境事件须使用各自固定排序键和冲突规则；不能只依赖数据库返回顺序。
7. **跨越多个时段。** 长动作跨 N 时段必须逐段推进并运行阶段 3–10；暂停/事件介入后应冻结或重新声明剩余计划，不能一次跳过中间状态。

## 六、P1-C 必须补齐的验收用例

| ID | 情境 | 预期 |
|---|---|---|
| CMD-01 | 权限/资格/资源前置不满足 | 拒绝，不写权威事实、不扣成本、不推进时段 |
| CMD-02 | 同一 requestId + 相同内容重试 | 返回原结果，不重复扣资源/时间 |
| CMD-03 | 同一 requestId + 改变目标/时间/payload | 幂等冲突，不追加第二事实 |
| CMD-04 | 两个不同 requestId 同一语义动作 | 按领域唯一性规则判断重复，不把请求幂等当业务幂等 |
| CMD-05 | 受理后执行人拒绝 | 记录任务结果/责任，不伪装成命令未发起 |
| CMD-06 | 受理后部分完成 | 已完成部分与已发生成本保留；未执行部分不预扣 |
| CMD-07 | 受理后资源不足/外部阻断 | 记录阻断原因与恢复/改派路径，不删除受理事实 |
| CMD-08 | 玩家撤回执行中任务 | 依批准规则释放未消耗预留，保留已发生成本和历史 |
| CMD-09 | 长动作跨 2+ 时段 | 每个中间时段依序结算；暂停时不继续推进 |
| CMD-10 | 任务完成与 dueAt 同边界 | 先完成检查点，再评估逾期；只产生一个终态 |
| CMD-11 | 多任务同 dueAt | 按稳定排序键处理，重放结果一致 |
| CMD-12 | 汛期边界与任务截止同一时段 | 环境阶段与任务阶段按已批准优先级处理，不覆盖各自状态 |
| CMD-13 | 承诺/债务与任务截止同一时段 | 阶段 3 与阶段 7 处理不同对象，不重复扣算 |
| CMD-14 | 迟报事件 | occurredAt 保留实际发生时间；recordedAt 保留写入时间；历史可追溯 |
| CMD-15 | 事件先发生后补录 | 账本 seq 保持写入顺序，业务发生时间不伪造为追加时间 |
| CMD-16 | 同一事实重复补录 | 依据领域唯一键/证据关系去重，不误删不同来源的独立报告 |
| CMD-17 | 世界暂停/玩家等待输入 | 世界时间、任务检查点、NPC 日程均不推进 |
| CMD-18 | 从 genesis 全量重放 | 任务状态、成本、期限、时间戳与最终投影完全一致 |

## 七、审计裁定

| 维度 | 结论 |
|---|---|
| 命令幂等与事件追加 | **工程基础通过**；业务唯一性规则仍由领域模块定义 |
| 命令校验与原子提交 | **当前预览通过**；通用多领域事务边界待扩展 |
| 发起前拒绝 vs 受理后失败 | **设计不通过**：成本边界缺统一裁定 |
| 异步任务生命周期 | **未形成完整契约**：10.7 仍标候选，当前 M1 不实现通用 Task |
| 期限对象与排序 | **不通过**：需与 P1-A 统一分域 |
| occurredAt / recordedAt | **不通过**：当前仅 requestWorldTime / committedAt，缺少迟报/补录语义 |
| 多时段动作与暂停恢复 | **原则通过，执行契约不完整** |
| 失败、撤回、部分完成与成本 | **不通过**：缺统一状态迁移和资源规则 |
| W5 账本/存档基线 | **保持**：本审计不要求重写，不提出无依据 schema 版本升级 |

**建议裁决：** 保持现有事件账本与 replay 内核；在领域契约层明确命令请求、受理任务、检查点、三类期限、资源预留和履行义务的边界；统一“发起前拒绝不产生业务成本”与“受理后失败按已发生事实结算”的原则；将 `requestWorldTime`、`occurredAt`、`recordedAt/committedAt`、`scheduledAt`、`dueAt` 分别定义，禁止互相代替。先由产品裁决，再设计 schema/测试；不得借本审计提前扩建完整 AI 世界运营者或事件锚点架构。

**当前结果：P1-C 审计完成，规则/schema 裁决未完成，代码施工不启动。**
