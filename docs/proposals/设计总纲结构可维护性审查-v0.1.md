# 设计总纲结构可维护性审查 v0.1

- **审查对象：** 根目录《设计总纲.md》v0.3
- **基线版本：** commit `873cd45cc707816b073660b4fe1f8660598c2520`
- **审查性质：** 静态文档结构审查；未进行代码、原型或游戏测试
- **状态：** 改进提案，待负责人审阅
- **原则：** 不拆散唯一权威源、不复制第二份总纲、不在本文件中擅自修改权威规则。

## 1. 结论摘要

当前总纲**产品方向和章节骨架清晰，跨模块契约与变更追踪能力尚未达到高效维护标准**。

它已经回答“做什么、为什么做、主要系统有哪些、M1 先验证什么”；尚未完全回答：
- 每条规则的唯一权威定义在哪；
- 每个模块消费哪些规则、向哪些模块提供什么；
- 哪些章节只是引用，哪些章节拥有修改权；
- 一条规则变化后，必须检查哪些章节、参数、例子、验收判据；
- 待裁决建议如何与已确认规则隔离；
- 同一规则在正文、参数表、JSON 示例和版本记录冲突时，按什么流程发现和解决。

因此，当前结构适合继续积累设计内容，但不宜在没有结构治理的情况下持续横向扩写。

## 2. 结构评分（文档审查判断，不是量化测试）

| 维度 | 判断 | 依据 |
|---|---|---|
| 产品愿景与核心循环 | 强 | 第 0–1 章有唯一核心循环、体验假设、首小时节拍和非目标 |
| 章节可导航性 | 较强 | 第 0–22 章分工基本可辨，主题覆盖完整 |
| 模块职责边界 | 中等 | 第 3–15 章按主题拆分，但动作、时间、认知、事件、记忆和 AI 事实边界跨章分布 |
| 模块接口/依赖显式程度 | 中偏弱 | 第 19 章概述模块与实现边界，但没有覆盖所有设计模块的统一输入/输出/依赖清单 |
| 规则唯一性 | 中偏弱 | 时间、事件、认知、因果记录分别出现在多个章节和附录示例中 |
| 决策治理 | 中等 | 第 20–22 章有待决事项、规则和版本记录，但缺少逐规则的稳定 ID 与跨章节影响映射 |
| 变更影响定位 | 偏弱 | 未见统一的“规则 ID → 权威章节 → 引用章节 → 参数 → 验收”的完整索引 |
| 验收闭环 | 中等 | 第 0.3、14.4、17.3 有假设/指标/场景判据，但尚未形成每条契约的验收映射 |
| 史实与参数可信度隔离 | 中等 | 有史料原则和待验证初值声明，但参数、制度假设、体验假设仍需更强分类标记 |

## 3. 当前结构的优点（应保留）

1. **核心循环前置。** 第 0 章先定义玩家体验，而不是先堆系统细节。
2. **非目标明确。** 第 1.3 和第 18 章有助于抑制范围膨胀。
3. **系统覆盖面完整。** 人物、关系、权限、仕途、行动、时间、执行、经济、事件、可读性、AI、行状和验证场景均有落点。
4. **验证场景收敛。** “一县、七人、十日、一汛”提供共同边界。
5. **已有治理意识。** 第 20–22 章明确待决事项、版本和唯一权威文件；这是后续升级的基础。

## 4. 主要结构问题

### S-01：模块正文与架构边界说明没有形成一一对应

第 3–15 章按玩法/系统主题展开，第 19 章再概括核心逻辑模块，但没有完整的模块目录证明两者一一对应。后续新增系统时，容易出现“正文已经定义业务规则，架构章却没有明确该规则归谁维护”的情况。

**建议：** 增加一张模块注册表（不一定增加大章，可放在第 19 章），每个模块固定填写：职责、非职责、权威数据、输入、输出/事件、依赖、被哪些模块引用、验收入口。

### S-02：关键基础概念跨章重复，缺少权威定义与引用关系

重点交叉：
- 时间/行动成本：第 4.5、8、9、20 章与附录 A；
- 认知/主张/记忆/证据/传闻：第 3.1–3.2、14.3、15.4、附录 B；
- 事件与因果记录：第 10.5、13.2–13.3、15.2、19.3、附录 B.3；
- 行政权限与行动意图：第 6、8、10 章；
- 人情债、关系变化和社会传播：第 4、13、14、15 章。

这些章节可以讨论同一概念，但必须区分“权威定义”“消费规则的解释”“UI 呈现”“示例”。目前仅靠读者理解，无法高效判定哪处拥有最终修改权。

**建议：** 每个跨模块概念设稳定规则 ID 与唯一权威定义位置。其他章节只写本模块特有规则，并显式引用 ID；发现冲突时先改权威定义，再逐一更新引用处。

### S-03：规则层、体验层、实现层和验证层混排

第 0 章有体验假设，第 3–15 章有领域规则，第 18 章有阶段计划，第 19 章有架构边界，第 20 章有决策治理，附录又有参数与数据结构。总体合理，但缺少从“设计规则”到“实现边界”再到“验证证据”的稳定链接。

**建议：** 不需要把所有内容拆成多个权威文件；保留总纲单一权威源，在每条重要规则下添加轻量标识：规则 ID、状态、依赖 ID、验证 ID。模块的详细提案可单独存在，但不得与总纲竞争权威性。

### S-04：附录中的数据示例可能反向制造规则

附录 B 的 Person、Debt、Event 示例具有字段和枚举的外观，容易被读者当作已冻结的数据契约；但正文中的认知、事件和成本语义仍有待裁决。例如 Event 示例内的行动成本、事实与人物所知字段会与正文定义发生耦合。

**建议：** 所有示例增加醒目标识“非规范示例/字段待裁决”，并列出其引用的规则 ID；真正冻结的结构另以“数据契约”状态标注，避免示例悄悄成为第二份规范。

### S-05：决策台账与正文之间缺少双向追踪

第 20 章已有待决事项与默认答案，第 22 章有版本记录，但无法仅凭统一索引快速回答：
- D-04 影响哪几处正文、哪几条模块提案？
- 修改第 9.1 后，哪些参数、动作、验收用例必须复查？
- 哪个体验指标验证某条规则，失败后回到哪条设计决策？

**建议：** 建立双向追踪表：规则 ID ↔ 权威章节 ↔ 引用章节/提案 ↔ 参数 ID ↔ 验收 ID ↔ 版本/决策记录。

### S-06：范围、假设和待验证参数的状态标记还不够细

文档总体声明参数为待验证初值，但单个规则或示例中的数值容易脱离上下文被复制。历史制度事实、设计假设、平衡初值和体验目标的证据等级不同。

**建议：** 至少区分：史实已核验、设计规则已批准、待裁决、待验证初值、示例/占位、已废弃。状态应贴近具体规则或参数，而不仅出现在章节开头。

## 5. 建议的目标结构（保留现有章节主体）

不建议立即大规模重排 1139 行正文，也不建议把总纲拆成多份相互竞争的“主文档”。建议采用“一个权威总纲 + 三张索引 + 提案/决策记录”的轻量结构：

1. **现有第 0–1 章：产品目标与范围**——保留。
2. **现有第 2 章：全局不变量**——保留；重要规则分配稳定 ID。
3. **现有第 3–16 章：领域模块**——保留章节主体；各章开头标注职责、输入、输出、依赖、权威规则 ID。
4. **现有第 17–18 章：验证场景与阶段范围**——保留；为每项体验假设和验收判据分配 ID。
5. **现有第 19 章：架构边界**——升级为模块注册表与依赖矩阵，不只写抽象原则。
6. **现有第 20 章：决策台账**——升级为规则状态和决策索引。
7. **现有第 21–22 章：治理与版本记录**——保留，增加变更影响报告约定。
8. **新增索引 A：规则目录**——规则 ID、唯一权威位置、状态、责任模块、依赖项。
9. **新增索引 B：模块依赖矩阵**——谁提供什么、谁消费什么、禁止依赖什么。
10. **新增索引 C：变更影响矩阵**——规则/模块/参数/验收/提案之间的双向追踪。

这三张索引可先作为总纲末尾表格或独立提案维护；在治理流程稳定前，不必引入复杂工具或数据库。

## 6. 推荐模块依赖方向

建议把依赖组织成单向链，禁止表达层反向修改规则状态：

**产品目标与范围**
→ **基础契约（时间、权限、身份、事件、认知）**
→ **领域规则（社交、委托、执行、经济、仕途、事件）**
→ **状态变化与事件记录**
→ **人物认知、记忆与社会传播**
→ **玩家可见信息与 UI**
→ **AI 自然语言表达**

补充约束：
- 关系与人情债不能绕过法定权限；
- 传闻不能直接变成客观事实；
- AI 叙述不能直接改写权威状态；
- UI 分类不能反向定义 NPC 认知；
- 参数表不能覆盖正文中的规则语义；
- 事件排序必须由共同契约定义，子模块只能声明事件类型和后果。

这是一项待批准的结构建议，不代表现有总纲已经完整满足该依赖方向。

## 7. 后期变更的标准流程建议

任何跨模块规则变更都按以下顺序执行：

1. **提出变更：** 标明规则 ID、原因、目标体验和当前问题。
2. **定位权威源：** 找到唯一权威定义；若存在多处冲突，先登记冲突，不直接任选一处覆盖。
3. **计算影响范围：** 查找引用章节、消费模块、相关参数、示例、验收项和其他提案。
4. **给出差异方案：** 明确改动、保留、废弃和兼容处理。
5. **检查依赖方向：** 确认没有新增循环依赖或重复权威源。
6. **更新追踪矩阵：** 所有受影响条目标记已处理或明确豁免理由。
7. **执行文档验收：** 术语一致、规则无冲突、边界闭合、验收可判定、状态标记正确。
8. **负责人批准后合入权威总纲：** 更新版本记录；提案与权威版本的关系明确可追溯。

## 8. 建议的文档级验收指标

| 指标 | 合格标准 |
|---|---|
| 权威定义唯一性 | 每条核心规则只有一个权威定义位置 |
| 规则可定位性 | 核心规则均有稳定 ID，可从 ID 找到定义与所有引用 |
| 模块边界完整性 | 每个核心模块均有职责、非职责、输入、输出、依赖、权威状态和验收入口 |
| 变更影响覆盖率 | 每次跨模块变更列出所有已知受影响项，未处理项必须有明确理由 |
| 冲突处理 | 所有已发现冲突均有责任人/决策状态，不静默覆盖 |
| 示例一致性 | 附录示例引用规则 ID，并明确是否规范性契约 |
| 状态清晰度 | 已批准、待裁决、待验证、示例、废弃可区分 |
| 验收可追溯性 | 核心体验假设和规则能关联到可判定的验证方法 |
| 范围控制 | 所有变更说明是否影响 M1“一县、七人、十日、一汛” |

## 9. 本轮不建议做的事

- 不立即把总纲拆成多个权威文件。
- 不以重排章节代替规则接口治理。
- 不先写复杂自动化工具；先建立稳定 ID 与追踪表。
- 不把本审查中的推荐方案当作已批准规范。
- 不声称代码、原型或游戏内验收通过。

## 10. 结论

《设计总纲》v0.3 的**章节骨架可保留，不需要推倒重写**。真正的优先改进是：

1. 设立唯一权威规则 ID；
2. 把第 19 章升级为真实的模块注册表和依赖矩阵；
3. 建立规则—模块—参数—验收的双向追踪；
4. 明确正文、提案、决策、参数和数据示例的规范地位；
5. 用变更影响报告替代凭记忆逐章查找。

完成以上工作后，后续改动才能从“全文搜索、人工猜测影响”转为“按规则 ID 精确定位，再对受影响模块做定向复审”。
