### 0.8 玩家可见性规则（`[C]`）

1. 玩家台账只显示玩家实际 `Exposure` 过的 Claim/Evidence。
2. NPC 只知道 0.4 表中“关键已知”，不能引用未接触材料。
3. AI 只能引用本次上下文提供的 ID；引用未提供 ID 视为幻觉，拒绝写入。
4. 送达 ≠ 阅读 ≠ 理解 ≠ 相信 ≠ 证实。
5. 行状/人物卡是投影，不是事实源；纠错靠新事件或新版本投影。

**目的：** 比较三种操作顺序，判断当前总纲能否唯一确定“D1 结束前拿到五份材料”的结果。

### A.1 初始状态

- 时间：D1晨。玩家疲劳 2。
- 目标：D1夜之前拿到五份材料：`R` 粮商口供、`Q1` 主簿口供、`C` 库房账册抄件、`Q2` 用账册质问主簿的口供、`V` 专家验堤结论。
- NPC 窗口：
  - `p_merchant`：仅 D1晨在铺面；D1午去码头。
  - `p_zb`：D1午在库房；D1暮在签押房；D1夜回宅，不见客。
  - `p_expert`：D1暮在堤上；其余时段不在县。
- 依赖：`Q2` 必须以 `C` 为引子；`C` 需要主簿在场；`V` 需要专家在场。
- 预算：玩家可支用 20 两；查账 5 两、发信 3 两（本场景不发信）。

### A.8 预期结果

1. **当前 main 不能唯一确定结果。** 同一组输入在 M1/M2/M3 三种口径下分别得到“五份不全 / 齐全 / 不全”，且 9.1 的身体状态阈值未定义，M2 本身也不确定。
2. 候选 C（1 动作/时段）确定，但会使 A1 的五动作链**不可能完成**；这不是规则错误，是内容节奏必须重写：主簿窗口应跨午/暮/次日，或把 Q1+Q2 合并为一次问话的两段。
3. 推荐：采用候选 C 的单一时段成本；M1 第一日的信息链压缩为 4 个动作，另设一条替代路径（如粮商口供可由书办旁证替代），避免“一步错、全案断”。

## 三、场景 C：任务完成与期限边界

**目的：** 用五个案例判定“到期”边界，禁止同一任务既完成又逾期（除非义务被显式拆开）。

| 失败分支 | C.7 |

### C.1 初始状态

- `task-t1` 盘料场，期限 `dueAt = D5暮`。
- 报告义务 `ob-report-t1`，期限 `D6晨`。
- 完成事件可能发生在 D5午 / D5暮 / D6晨。
- 完成判定看 `occurredAt`，不看 `recordedAt`。

### C.1.1 玩家输入（五个测试命令）

| 案例 | commandId | 输入 | 备注 |
|---|---|---|---|
| C1 | `cmd-c-0001` | 提交完成，`occurredAt=D5午` | 提前完成 |
| C2 | `cmd-c-0002` | 提交完成，`occurredAt=D5暮` | 压线 |
| C3 | `cmd-c-0003` | 提交完成，`occurredAt=D6晨` | 逾期 |
| C4 | `cmd-c-0004` | 提交失败，`occurredAt=D5午` | 书办 D6晨补记 |
| C5 | `cmd-c-0005`（重复两次） | 同 C1 完成 | 第二次应 no-op |

### C.1.2 规则前置

1. 任务已受理，进度 = 3/3，执行人可交付。
2. 完成命令必须带 `occurredAt`；报告是独立命令/义务。
3. `dueAt = D5暮`；判定统一按 ADJ-006 的边界（推荐时段末，含）。
4. 重复完成按 `(taskId, completionEventId)` 幂等；第二次不改变状态。
5. 失败命令也必须带 `occurredAt`；`recordedAt` 只作审计。

### C.2 五个案例

| 案例 | 完成 occurredAt | 记录 recordedAt | 工作义务判定 | 报告义务判定 | 结论 |
|---|---|---|---|---|---|
| **C1 提前完成** | D5午 | D5午 | 按时 | D6晨按时 | 双按时 |
| **C2 边界完成** | D5暮 | D5暮 | **候选：按时**（dueAt 为时段末）；替代：逾期（dueAt 为时段初） | D6晨按时 | 取决于边界定义 |
| **C3 逾期完成** | D6晨 | D6晨 | 逾期 1 段 | 报告无法同段提交（1 时段），D6午交 → 逾期 | 双逾期，但分别计算 |
| **C4 完成前失败** | 失败 D5午 | D6晨补记 | 失败发生在期限内；记录延迟是另一项文书过错 | 报告 D6晨说明失败 → 按时 | 不发生“完成”，也不发生“逾期完成” |
| **C5 重复完成** | D5午（两次） | D5午 | 第一次有效；第二次 no-op | 一次 | 不重复奖励/扣款 |

### C.3 逐案例结算

#### C1

```
D5-morning  task-t1 progress 3/3
D5-noon     evt-c1-done  occurredAt=D5-noon  dueAt=D5-dusk  verdict=on_time
D6-morning  evt-c1-report  ob-report-t1  submitted  verdict=on_time
```

#### C2

- 候选定义：`dueAt` 是**该时段结束**。`occurredAt = D5暮 ≤ dueAt = D5暮` → 按时。
- 替代定义：`dueAt` 是**该时段开始**。`occurredAt = D5暮 > D5暮` → 逾期。
- 同一事件、同一字段，两种定义得出相反结果；当前 main 未定义，必须裁决。
- 若同段还要提交报告：报告动作 1 时段，不能与完成同段，必须 D6晨；因此报告义务与工作义务必须分开。

#### C3

```
D6-morning  evt-c3-done  occurredAt=D6-morning  verdict=overdue_by_1_period
D6-morning  ob-report-t1  due  → 需要 1 时段
D6-noon     evt-c3-report  submitted  verdict=overdue_by_1_period
```

- 工作逾期与报告逾期是两条记录，不合并成“任务逾期两次”。

#### C4

```
D5-noon  evt-c4-fail  occurredAt=D5-noon  reason=gentry_blockade
D6-morning  evt-c4-record  recordedAt=D6-morning  note=clerk_delayed
```

- 失败发生在期限内；`recordedAt` 晚不改变失败时点。
- 报告 D6晨按时；但“延迟记录”可被上司视为文书不谨，另计小过。

#### C5

```
D5-noon  evt-c5-done-1  accepted
D5-noon  evt-c5-done-2  rejected reason=DUPLICATE_COMPLETION
```

- 幂等键：`(taskId, completionEventId)`；重复事件不改变状态。

### C.5 玩家可见信息

- 任务卡显示“完成：D5暮（边界）”“报告：D6晨（未交）”，不把两者合成一个“逾期”红字。
- 若 C2 采用“时段末”定义，界面写“压线完成”；若采用“时段初”，写“逾期 1 段”。文案必须与规则一致。

### C.6 预期结果

1. `dueAt` 的边界语义必须写死，否则 C2 无法唯一判定。
2. 工作完成与报告提交是**两个义务**；不拆开就会出现“既完成又逾期”。
3. `occurredAt` 与 `recordedAt` 必须分开；否则书记晚记一天就能改变成败。
4. 重复完成必须幂等。

### C.7 失败分支

| C-F4 重复提交 | 玩家重复点“完成” | 第二次拒绝，不扣资源 |

- ADJ-007：工作义务与报告义务是否强制拆分。
- ADJ-008：`occurredAt`/`recordedAt` 的权威性与补记规则。

1. `commandId` 未见过，或同 ID 且参数哈希一致（重放）。
2. `expectedWorldVersion = 12` 与当前版本一致。
3. 知县有委托权；县丞在县；预算 20 ≤ 可用额度。
4. 阶段 0 校验通过后才进入阶段 1；前置失败不扣时间/资源。
5. 命令日志、任务、预留、事件、版本必须在同一事务提交。
6. 模型/自然语言解析只能产生候选意图，不能绕过本校验。

### D.3 六种情况

| 情况 | 输入 | HTTP/业务码 | 世界变化 | 命令日志 | 返回 |
|---|---|---|---|---|---|
| **D1 首提** | 基准命令 | 200 `ACCEPTED` | 创建 task-t1、res-1=20、evt-d-0001；版本 12→13 | `cmd-d-0001: accepted` | `{taskId, reservationId, eventId, worldVersion:13}` |
| **D2 同 ID 重放** | 完全相同 | 200 `REPLAYED` | **无**；版本仍 13 | 原记录 | **同一** `{taskId, reservationId, eventId, worldVersion:13}` |
| **D3 同 ID 改参** | budgetCap=30 | 409 `COMMAND_ID_CONFLICT` | 无 | 追加 `conflict` 记录，不改原记录 | 错误：原命令参数不同 |
| **D4 前置失败** | 县丞不在县 | 422 `PRECONDITION_FAILED` | 无；不扣时不扣钱 | `cmd-d-0004: rejected` | `{rejectionCode:"ASSIGNEE_ABSENT", rejectionId}` |
| **D5 提交后失败** | 受理后县丞拒办 | 200 `ACCEPTED` 后异步 `FAILED` | 扣玩家 1 时段；释放 res-1；`evt-d-0005-fail` | `accepted` → `failed` | 失败事件 ID + 释放金额 |
| **D6 事务中途不一致** | 事件写入成功、任务行写入失败 | 500 `TRANSACTION_FAILED_RETRYABLE` | **全部回滚**；版本仍 12 | 不写 accepted；写 `attempt_failed` | 可重试；同 ID 重试只执行一次 |

### D.4 逐情况结算

#### D1 首提

```
阶段 0：commandId 未见过；expectedWorldVersion=12 匹配；权限/资格/资源通过
阶段 1：事务 {
  insert task-t1(status=accepted)
  insert res-1(amount=20, status=reserved)
  insert evt-d-0001(type=task_created)
  insert command_log(cmd-d-0001, status=accepted, resultRef=task-t1)
  worldVersion 12→13
}
```

#### D2 重放

- 命中 `commandId` 唯一索引；参数哈希一致 → 返回原结果，不进入阶段 1。
- 不重复扣 20，不重复创建 task，不重复推进时段。
- 日志只加一条 `replayed` 审计记录，不算世界事件。

#### D3 同 ID 改参

- 参数哈希不一致 → 409；不覆盖原命令，不创建 task-t1b。
- 玩家要改预算，必须用新 `commandId`（如 `cmd-d-0003`），并显式取消/修改原任务。

#### D4 前置失败

- 校验在阶段 0 完成；不进入阶段 1。
- 不扣 1 时段、不扣 5 两、不创建任务、不推进世界。
- 拒绝结果也要幂等：同 ID 重放返回同一 `rejectionId`。
- 与“提交后失败”区分：后者已消耗时间，必须写具体失败事件（如 `evt-d-0005-fail`）。

#### D5 提交后失败

```
D2-morning  cmd-d-0005 accepted; 玩家 -1 时段; res 20
D2-noon     evt-d-0005-fail; res released 20; task failed; worldVersion +1
```

- 失败原因是执行层（拒办/无料/被阻），不是前置校验。
- 时间已花，不能退回；预算释放，不能算支出。

#### D6 事务中途不一致

两种错误实现：

| 实现 | 现象 | 后果 |
|---|---|---|
| 命令日志在事务外先写 | 日志 accepted，任务未创建 | 重放返回“已受理”，但世界无任务 → 幽灵命令 |
| 事件先提交、任务后提交 | 事件存在，任务不存在 | 账/任务/事件三方不一致 |
| **正确：单事务** | 日志、任务、预留、事件、版本同一事务 | 失败全回滚；可安全重试 |

重试：

```
attempt 1: 500 TRANSACTION_FAILED_RETRYABLE（无 accepted 记录）
attempt 2: 同 cmd-d-0006 → 正常执行一次 → accepted
```

### D.5 ID 关系

| ID | 含义 | 是否可复用 | 示例 |
|---|---|---|---|
| `commandId` | 一次玩家请求 | 否；同 ID 只能同参重放 | `cmd-d-0001` |
| `taskId` | 业务对象（委托任务） | 否；一个任务一个 ID | `task-t1` |
| `eventId` | 已发生事实 | 否；追加式 | `evt-d-0001` |
| `reservationId` | 预算预留 | 否 | `res-1` |
| `rejectionId` | 拒绝记录 | 否 | `rej-d-0004` |
| `worldVersion` | 乐观并发版本 | 每次事务 +1 | 12→13 |

### D.6 玩家可见信息

- 成功：显示任务卡、预算预留、承办人、期限。
- 重放：界面不重复弹“已受理”，只显示原结果 + “已处理”。
- 同 ID 改参：提示“该操作已提交，不能改参数；请新建一条委托”。
- 前置失败：说明缺哪一项（人不在/钱不够/无权限），给替代路径。
- 提交后失败：显示失败原因、已耗时段、预算已释放。

### D.7 预期结果

1. 首提与重放必须返回同一业务结果，且世界只变一次。
2. 同 ID 改参必须拒绝，不能“最后一次覆盖”。
3. 前置失败零成本；提交后失败按动作声明扣成本。
4. 事务边界必须同时覆盖命令日志、业务对象、预算、事件、版本；否则会出现幽灵命令。
5. `commandId`/`taskId`/`eventId` 不能混用；日志里必须三列并存。

### D.8 失败分支

| 分支 | 触发 | 结果 |
|---|---|---|
| D-F1 超时重试 | 客户端未收到响应，带同 ID 重试 | 返回原结果；不重复扣款 |
| D-F2 版本冲突 | 另一命令已把版本推到 13 | 409 `VERSION_CONFLICT`；提示刷新后重提（新 commandId） |
| D-F3 部分写入 | 事件成功、任务失败 | 回滚；不得留下孤儿事件 |
| D-F4 重复失败 | 同 ID 第二次提交后失败 | 返回同一失败结果，不重复扣时 |

### D.9 待裁决

- ADJ-009：命令日志是否与世界状态同事务；幂等键范围。
- ADJ-010：前置失败与提交后失败的边界及成本策略。
- ADJ-011：乐观并发（worldVersion）是否为 M1 必需。

## 五、场景 E：远距通信的认知链（M1 外推测试）

> **范围声明：** 本场景发生在江苏—京师，**不属于 M1 内容**。它只用于验证“送达/阅读/理解/相信/证实”字段是否足以支撑远距通信；不得据此扩张 M1。

### E.0 场景要素

| 要素 | 位置 |
|---|---|
| 初始状态 | E.1 |
| 玩家输入 | E.2 |
| 规则前置 | E.2.1 |

| 失败分支 | E.7、E.10 |

### E.1 初始状态

- 玩家：江苏某县知县 `p_mag_e`（外推，不是 M1 的知县）。
- 友人：`p_wang`，原在京师宣武门外旧宅；一个月前调通州张家湾，玩家不知道。
- 玩家认知：三个月前收到王主事来信，地址为旧宅；`[K]` 置信度中；`[Q]` 记录“王在京师旧宅”。
- 客观事实：王已迁通州；旧宅邻居可转信；转信需 2 日。
- 信道：托人捎带（非驿递）；单程 12 日；费用 3 两；可靠性中。

### E.2 玩家输入

```json
{
  "commandId": "cmd-e-0001",
  "actorId": "p_mag_e",
  "intent": "send_letter",
  "payload": {
    "recipientId": "p_wang",
    "address": "京师宣武门外旧宅",
    "contentClaimIds": ["clm-e-river-funds", "clm-e-request-help"],
    "channel": "private_courier",
    "cost": { "time": 1, "silver": 3 }
  },
  "expectedWorldVersion": 5
}
```

### E.2.1 规则前置

1. 玩家只知道收信人三个月前的旧地址，置信度中；不能读取客观位置。
2. 信道可用：私托，1 时段 + 3 两；单程 12 日，转信 +2 日。
3. 玩家不能直接读取收信人的阅读/理解/信念；只能通过回信或独立渠道获知。
4. 送达、阅读、理解、相信、证实各自需要独立事件，不得自动推导。
5. 回信丢失时，玩家台账不得自动变成“已读”。

### E.3 认知状态机

```
composed → sent → in_transit → delivered_old → forwarded → delivered_new
         → read → understood → belief(accept/reject/suspend) → replied
```

每一跳都是独立事件；任何一跳缺失，后续状态不得自动推导。

### E.4 逐日结算

| 时间 | 事件 | 客观状态 | 玩家台账 | 备注 |
|---|---|---|---|---|
| D1晨 | `evt-e-sent` | 信交出；3 两；1 时段 | 已送出 | 玩家只知道“送出” |
| D1–D12 | 在途 | 信在路上 | 已送出 | 无回执 |
| D13午 | `evt-e-delivered-old` | 送到旧宅 | 仍“已送出” | 玩家不知道已送达 |
| D13暮 | `evt-e-forwarded` | 邻居转寄通州 | 仍“已送出” | 转信人不是王 |
| D15午 | `evt-e-delivered-new` | 到张家湾 | 仍“已送出” | |
| D15暮 | `evt-e-read` | 王拆阅 | 仍“已送出” | 阅读≠相信 |
| D15夜 | `evt-e-understood` | 王理解“河工银被劫”是请求-help 的由头 | 仍“已送出” | |
| D16晨 | `evt-e-belief` | 王对“河工银被劫”存疑（reject 0.7） | 仍“已送出” | 信念是王的，不是玩家的 |

### E.5 玩家可见信息 vs 客观事实

| 时点 | 玩家以为 | 客观 | 差距来源 |
|---|---|---|---|
| D1–D12 | 信在路上 | 在途 | 正常 |
| D13–D27 | 信可能已到，王未回 | 已转寄、已读 | 无回执；玩家不能假设“未回=没读” |
| D28 | 王在通州，且对“被劫”存疑 | 同左 | 回信带来新地址与新主张 |
| D28 之前 | 王仍在旧宅 | 王已迁 | 三个月前的旧信息 |

### E.6 送达/阅读/理解/相信/证实

| 状态 | 定义 | 本场景事件 | 能否由前一状态推导 |
|---|---|---|---|
| 送达 | 到达可达地点/接收对象 | `delivered_old` / `delivered_new` | 不能由“送出”推导 |
| 阅读 | 接收者实际拆阅 | `read` | 不能由“送达”推导 |
| 理解 | 接收者按发送者意图解读 | `understood` | 不能由“阅读”推导 |
| 相信 | 接收者对主张的立场 | `belief` | 不能由“理解”推导 |
| 证实 | 用独立证据核验 | 玩家收到回信+官方邸报确认调动 | 不能由“相信”推导 |

### E.7 六条分支

| 分支 | 触发 | 结果 | 玩家能否知道 |
|---|---|---|---|
| E1 无人转信 | 旧宅邻居搬走 | 信滞留旧宅；永远 `delivered_old` | 不能；只能从“久无回信”推测 |
| E2 转信丢失 | 邻居转寄途中丢失 | 不到通州 | 不能 |
| E3 读到但不信 | 王认为“被劫”是托词 | `read`+`understood`+`belief=reject` | 只能等回信；回信可能责备 |
| E4 回信丢失 | 回程丢包 | 王已读，玩家永不知道 | 玩家台账保持“已送出” |
| E5 传闻先到 | 同行商人传“知县被参” | 玩家听到失真版本 | 玩家需判断来源；传闻不是事实 |
| E6 地址核实 | 玩家另发公函到通州衙门 | 得到官方确认 | 可升级为“已核实” |

### E.8 传闻失真示例

```
原始 Claim：知县因河工银被劫，向上官请求展限。
一跳：知县河工银出了问题。
二跳：知县河工银被参。
三跳：知县已被革职。
```

- 每一跳记录 `hopChain`、`arrivedAt`、`distortionEvents`。
- 玩家台账对“已被革职”标“听说”，来源可靠性“低”；不得标“已核实”。
- 即使后来证明“被参”为假，传闻链仍保留，作为“谁在放风”的证据。

### E.9 预期结果

1. 远距通信必须至少七态；任何“送到即知道、读到即相信”的简化都会导致 AI 越权。
2. 玩家台账只反映玩家实际接触；不能因为世界事实是“王已迁”就自动更新。
3. 回信是唯一可靠回执；没有回信时，“未回”不能推出“未读”。
4. 信道耗时、费用、可靠性都是待定参数；本场景不提供 M1 数值。

### E.10 失败分支

| 分支 | 触发 | 结果 |
|---|---|---|
| E-F1 地址错误且无转信 | 邻居不在 | 信退回或滞留；1 时段+3 两已花 |
| E-F2 误信传闻 | 玩家把“被革职”当真 | 可能做出错误决策；台账标“听说”可降低误判 |
| E-F3 催问过频 | 玩家连发三信 | 每封 1 时段+3 两；王可能反感，关系 −1 |
| E-F4 用官驿发私信 | 越权使用驿递 | 被参风险；不是合法信道 |

### E.11 待裁决

- ADJ-012：送达/阅读/理解/相信/证实的状态机是否写入正式契约。
- ADJ-013：信道参数（耗时、费用、可靠性、丢失率）是否进入 M1；若不进入，M1 只保留同城/在场通信。
- ADJ-014：玩家台账四档与来源可靠性的升级规则。

### G.5 随机复现

```text
roll(event) = HMAC(seed, ruleVersion + "|" + poolVersion + "|" + eventId) mod 100
seed = m0-2026-10-29
ruleVersion = v0.4+candidate-2026-10-29
poolVersion = m0-pool-1
```

| 事件 | roll | 命中区间 | 结果 |
|---|---|---|---|
| `evt-flood-warning` | 37 | 0–59 水位升 1 尺 | 预警 |
| `intent-xc-patrol` | 82 | 60–99 发现湿痕扩大 | 县丞报告“3 处变 4 处” |
| `intent-zb-ledger` | 14 | 0–49 账册可交 | 主簿交册 |
| `rum-g-1` | 55 | 0–69 传到县衙 | 知县听到 |
| `ob-debt-1` | 08 | 0–89 粮商愿收 | 收款 |
| `evt-g-entry` | 91 | 90–99 士绅联名 | 递状 |

- G1 若按遍历顺序连续调用 RNG，NPC 与任务插入会改变后续事件的 roll；同一 seed 复现出不同结果。
- G2 每个事件用 `eventId` 派生独立 roll，插入顺序不影响结果。

### G.6 跨时段推进

```
D4夜 → D5晨（阶段 3–10）→ D5午（阶段 3–10）→ D5暮（阶段 3–10）→ D5夜（阶段 3–10）
```

- 不得从 D4夜 直接跳到 D5暮；每个时段都要跑任务/环境/NPC/认知/期限/导演/夜间。
- 玩家 D5暮 的 `cmd-g-pay` 在阶段 1 提交，响应 `worldVersion:41`；后续阶段都基于 41。
- 若玩家用 `expectedWorldVersion=40` 在 D5夜再提交，返回 `VERSION_CONFLICT`。

### G.7 导演不追溯

- 士绅联名在 D5暮 被“发现”，但事件 `triggerAt=D6晨`。
- D5暮 的结算不得引用 `evt-g-entry` 的结果；只能把它排入 D6晨 的候选池。
- 若导演事件要改变 D5暮 的传闻，必须另发新事件，不能改写 `rum-g-1`。

### G.8 夜间不是第二时钟

夜间只做：

1. 睡眠时长/质量；
2. 疲劳恢复；
3. 次日可用时段/状态；
4. 到期的承诺与债务（已在阶段 7 结算的，不重复）；
5. 三行摘要。

夜间**不得**：

- 重新跑任务完成；
- 重新判逾期；
- 重新抽导演事件；
- 修改已提交事件。

### G.11 预期结果

1. 同一时段必须有唯一阶段顺序；否则同一 seed 也会出不同结果。

5. 导演只能排未来，不能改写已提交事件。
6. 玩家动作必须带 `expectedWorldVersion`，避免基于旧状态提交。

### H.3 八个边界案例

#### H1：高可靠 + 敌对 + 假话

- `s-zb` 可靠性高，但 `clm-1` 是假。
- 玩家状态只能是“听说”；不能因为“主簿经手账目”就标“已核实”。
- 只有拿到 `evd-ledger` + `evd-receipt` 对不上，才可转“已核实（假）”。

#### H2：低可靠 + 友好 + 真话

- `s-baofu` 说“湿痕在扩大”，可靠性中，但为真。
- 玩家状态“听说”；若玩家亲去看到 4 处湿痕，才可“已核实”。
- 友好不提升可靠性；真话也不自动升级。

#### H3：两个独立来源一致

- `s-merchant` 与 `s-baofu` 都说“料不够”。
- 两口头来源一致 → 最多“推测”，不自动“已核实”。
- 要“已核实”，需文书/亲验（如 `evd-receipts` 30 垛）。

#### H4：立场变化

- 玩家压主簿，主簿立场从“自保”转“恐惧/服从”。
- 可靠性不变（仍高）；`q-1` 状态不变（仍听说）。
- 不能因为“他服了”就认为他说的是真话。

#### H5：已核实后翻案

- `q-4` 原“已核实”（亲验闸底）。
- 后证明探挖记录被专家夸大（新证据 `evd-counter`）。
- 状态降为“存疑”；保留原核实记录与降级原因。
- 不允许静默删除原记录。

#### H6：玩家告知 NPC

- 玩家把 `q-4` 告诉县丞。
- 县丞获得新 `Exposure`，其 `Belief` 可更新为“存疑/接受”。
- 玩家台账不变；县丞不能引用玩家未说出的 `q-2`。
- AI 上下文只含县丞已接触的 ID。

#### H7：敌对话真

- `s-gentry` 放风“知县被参”，后来证明“被参”为真。
- 玩家状态从“听说”可升“已核实”，但必须靠独立证据（如札文），不能因为“后来应验”就自动升级。
- 来源立场仍敌对；可靠性仍中。

#### H8：四档状态与“只降不升”

- 当前 main 14.3 写“只降不升，除非出现新证据”。
- 本测试：`q-1` 从“听说”→“已核实（假）”，是升级（核验度提高）但同时是证伪；若系统把“已核实”理解为“为真”，就会出错。
- 结论：四档是**核验状态**，不是真伪值；“已核实”应允许“已核实为假”。候选契约需补这一语义。

### H.4 状态转移表

| 触发 | 前 | 后 | 允许 | 条件 |
|---|---|---|---|---|
| 首次听到 | 无 | 听说 | 是 | 有来源 |
| 玩家推断 | 听说 | 推测 | 是 | 有推理依据 |
| 亲验/硬证 | 听说/推测 | 已核实（真/假） | 是 | 证据 ID |
| 与已知冲突 | 已核实 | 存疑 | 是 | 冲突证据 |
| 新证据 | 存疑 | 已核实 | 是 | 新证据 |
| 同一传闻重复 | 听说 | 听说 | 是 | 置信度可微调，不升级 |
| 来源立场变好 | 任意 | 不变 | 否 | 立场≠可靠性 |
| 来源可靠高 | 无 | 听说 | 是 | 仍不自动核实 |

### H.5 预期结果

1. 来源立场、来源可靠性、玩家情报状态必须三列分开。
2. 高可靠来源也会说谎；友好来源也会错；敌对的来源也可能说真话。
3. “已核实”是核验状态，不是“为真”；必须允许“已核实为假”。
4. 传闻重复不升级；立场变化不升级；只有新证据/亲验才升级。
5. 玩家告知 NPC 只是新 `Exposure`，不是复制信念。

| H-F5 已核实=为真 | 证伪时无法表达 | 台账失真 |
